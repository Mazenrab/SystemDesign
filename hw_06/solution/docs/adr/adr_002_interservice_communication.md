# ADR 002: Межсервисное взаимодействие в критических сценариях

## Статус
Принято (Accepted)

## Контекст и проблема
В рамках выбранной микросервисной архитектуры ([ADR 001](./adr_001_architecture_style.md)) необходимо организовать надежное, отказоустойчивое и быстрое взаимодействие между ключевыми бизнес-доменами: сервисом каталога, сервисом бронирования, сервисом оплаты и сервисом уведомлений.

Основная проблема заключается в обеспечении консистентности данных в критических сценариях (например, цепочка: *«Пользователь нажал купить -> Место заблокировано -> Платеж проведен -> Место выкуплено окончательно -> Билет сгенерирован и отправлен»*) в условиях экстремальных пиковых нагрузок (Flash Sales), когда недопустимы как потеря сообщений, так и зависание клиентских запросов.

## Рассматриваемые альтернативы

### 1. Чистое синхронное взаимодействие (REST API / gRPC)
Все сервисы общаются друг с другом напрямую по протоколам HTTP/REST или gRPC в режиме ожидания ответа (Request-Response).

*   **Плюсы:**
    *   Простота реализации, отладки и тестирования. Поток выполнения линеен.
    *   Мгновенное подтверждение успешности или ошибки операции от зависимого сервиса на каждом шаге.
*   **Минусы:**
    *   **Каскадные сбои:** Отказ сервиса нотификаций или генерации билетов заблокирует завершение транзакции оплаты на клиенте.
    *   **Рост Latency:** Итоговое время ожидания пользователя на фронтенде складывается из суммы времен ответов всех участвующих в цепочке бэкенд-сервисов.
    *   **Жесткая связность:** Сервис оплаты должен явно знать сетевые адреса и API смежных сервисов.

### 2. Асинхронное взаимодействие на базе событий (Event-Driven через Apache Kafka)
Сервисы общаются исключительно путем публикации событий (Events) в распределенный лог сообщений. Сервисы-источники ничего не знают о своих потребителях.

*   **Плюсы:**
    *   **Слабая связность (Loose Coupling):** Сервис оплаты просто публикует событие `OrderPaid`. Кто его слушает (сервис билетов, сервис аналитики, сервис CRM) — его не касается.
    *   **Высокая отказоустойчивость:** Если сервис нотификаций «лежит», Kafka сохранит сообщения. Как только сервис поднимется, он дочитает лог и отправит билеты без потери данных.
    *   **Асинхронный бэклог (Throttling):** Защита downstream-сервисов от пиковых нагрузок за счет регулирования скорости чтения (Consumer Rate).
*   **Минусы:**
    *   **Eventual Consistency (Консистентность в конечном итоге):** Пользователь не видит билет на экране мгновенно, данные обновляются с задержкой.
    *   **Сложность отладки:** Отслеживание распределенных логов требует внедрения сквозной трассировки (Correlation ID).

### 3. Синхронная оркестрация через Saga-паттерн без брокера (Temporal / Camunda / Оркестратор через gRPC)
Выделенный сервис-оркестратор последовательно вызывает другие сервисы по gRPC. В случае сбоя на одном из этапов, оркестратор последовательно вызывает компенсирующие транзакции (отмена брони, возврат средств).

*   **Плюсы:**
    *   Централизованный контроль бизнес-логики. Весь сценарий покупки билета описан в одном месте (коде оркестратора).
    *   Быстрое межсервисное взаимодействие за счет бинарного протокола gRPC / HTTP/2.
*   **Минусы:**
    *   Оркестратор становится «супер-сервисом» (God Object) и единой точкой отказа.
    *   Высокая нагрузка на сеть и уязвимость перед лавинообразным ростом запросов во время Flash Sales — сервисы могут забить пулы потоков друг друга.

### 4. Гибридный подход: Синхронное ядро + Асинхронный периферийный контур (Выбранный вариант)
Разделение взаимодействий по типу операций:
1. Квазисинхронные транзакционные операции (внутри контура бронирования и инициации оплаты) координируются оркестратором.
2. Все пост-оплатные, аналитические и тяжелые фоновые процессы (генерация бланков билетов, отправка Email, пушей, обновление витрин данных) переводятся на Event-Driven архитектуру через Kafka.

*   **Плюсы:**
    *   Идеальный баланс: пользователь получает мгновенный HTTP-ответ `202 Accepted` («Ваш платеж принят, билет формируется»), транзакционное ядро работает быстро, а тяжелые задачи не аффектят основной поток.
    *   Оптимальное использование ресурсов инфраструктуры.
*   **Минусы:**
    *   Необходимо поддерживать два разных паттерна интеграции (gRPC-клиенты и Kafka producers/consumers).

## Решение
Выбран **Вариант 4: Гибридный подход**. 
*   Для критических синхронных запросов чтения, где важна минимальная задержка (проверка доступности мест в зале, валидация штрих-кода билета на турникете стадиона), используется **gRPC**.
*   Для сквозных бизнес-процессов (оплата, фиксация выкупа, генерация и отправка билета) используется **асинхронный Event-Driven подход на базе Apache Kafka**.

## Обоснование
Асинхронность в пост-оплатном контуре позволяет разгрузить систему в моменты пиковых распродаж. Когда пользователь успешно оплачивает заказ, платежный шлюз уведомляет Сервис Оплаты, который моментально публикует событие `OrderPaid` в Kafka и возвращает пользователю экран успеха. 

Сервис Бронирования (снимает TTL-блокировку и закрепляет место навсегда) и Сервис Уведомлений (генерирует push и шлет email) подписаны на этот топик и обрабатывают сообщение независимо. Сбой в отправке email никак не влияет на факт успешной покупки билета пользователем.

## Последствия
1.  **Инфраструктура брокера:** Требуется развертывание, мониторинг (метрики лага консьюмеров) и обеспечение высокой доступности кластера Apache Kafka (минимум 3 реплики для топиков биллинга с параметром `acks=all`).
2.  **Идемпотентность (Idempotent Consumer):** Сетевые сбои в Kafka могут приводить к повторной доставке сообщений (доставка *at-least-once*). Все сервисы-потребители обязаны реализовывать паттерн Идемпотентного Потребителя (например, проверка уникального `payment_id` / `booking_id` в базе данных перед обработкой события), чтобы избежать повторного списания или дублирования билетов.
3.  **Паттерн Transactional Outbox:** Чтобы исключить ситуацию, когда запись в БД сервиса прошла успешно, а отправка события в Kafka упала (или наоборот), внутри сервисов необходимо внедрить паттерн **Transactional Outbox** (сохранение события в локальную таблицу БД в рамках той же ACID-транзакции с последующей отправкой в Kafka отдельным релеем).
4.  **Сквозной трейсинг:** Потребуется настроить проброс `Correlation ID` через метаданные (Headers) сообщений Kafka для сквозного логирования всей цепочки.
