# ADR 002: Межсервисное взаимодействие в критических сценариях

## Статус
Принято (Accepted)

## Контекст и проблема
В микросервисной архитектуре необходимо организовать надежное взаимодействие между сервисом бронирования, сервисом оплаты и сервисом уведомлений без потери сообщений и жесткой связности.

## Рассматриваемые альтернативы
1. **Синхронное взаимодействие (REST / gRPC)**
   - *Плюсы:* Простота реализации, мгновенный ответ от зависимого сервиса (Request-Response).
   - *Минусы:* Каскадные сбои при отказе одного из сервисов. Повышение времени ответа системы из-за ожидания по цепочке.
2. **Асинхронное взаимодействие на базе событий (Event-Driven с Message Broker)**
   - *Плюсы:* Слабая связность (Loose Coupling), высокая отказоустойчивость, гарантированная доставка сообщений при использовании постоянного хранилища брокера.
   - *Минусы:* Eventual Consistency, сложность отладки и трассировки запросов.

## Решение
Выбран **Event-Driven подход с использованием Apache Kafka** в качестве брокера сообщений для большинства бизнес-процессов (оплата, отправка билета). Для синхронных запросов чтения (проверка баланса, валидация билета на входе) будет использоваться **gRPC**.

## Обоснование
Асинхронность позволяет разгрузить систему. Когда пользователь оплачивает билет, сервис оплаты публикует событие `OrderPaid`. Сервис бронирования и сервис уведомлений подписываются на него и обрабатывают транзакцию независимо, не заставляя пользователя ждать отправки email.

## Последствия
- Требуется развертывание и поддержка кластера Apache Kafka.
- Необходимо реализовать паттерн Idempotent Consumer для предотвращения повторной обработки сообщений.
