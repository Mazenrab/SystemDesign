# ADR 006: Механизм резервирования мест и управления TTL бронированиями

## Статус

Принято (Accepted)

## Контекст и проблема

Главный инвариант билетной системы — полное исключение двойных продаж (double-booking). Одно и то же место на мероприятии не может быть зарезервировано или продано двум разным пользователям ни при каких обстоятельствах.

При этом нагрузка на систему бронирования распределена крайне неравномерно: в моменты старта продаж билетов на популярные события тысячи пользователей одновременно пытаются захватить одни и те же лучшие места.

Бизнес-требование накладывает условие: выбранное место должно блокироваться в пользу покупателя ровно на **10 минут** для проведения оплаты. Если по истечении этого времени транзакция не завершилась успехом, место должно автоматически и мгновенно вернуться в открытую продажу. Таким образом, операция резервирования представляет собой транзакционный процесс с таймером (TTL), выполняющийся в условиях экстремально высокой конкуренции за ресурсы.

## Рассматриваемые альтернативы

### 1. Пессимистичные блокировки на уровне СУБД (PostgreSQL `SELECT ... FOR UPDATE`)

* **Плюсы:**

  * **Максимальная надежность:** Использование встроенных ACID-механизмов реляционной СУБД гарантирует абсолютную консистентность "из коробки".
  * **Простота реализации:** Отсутствие необходимости в координации внешних инфраструктурных компонентов.
* **Минусы:**

  * **Исчерпание ресурсов базы данных:** Удерживать заблокированными строки инвентаря в транзакции на протяжении всех 10 минут (пока пользователь вводит данные карты) категорически неприемлемо. Это приведет к быстрому исчерпанию пула соединений СУБД.
  * **Деградация производительности:** Приводит к образованию огромных очередей ожидания на СУБД, вызывая лавинообразный рост задержек и падение системы в пиковые моменты.

### 2. Резервирование исключительно in-memory 

* **Плюсы:**

  * **Крайне высокая скорость:** Обработка сотен тысяч запросов в секунду с более низкой (по сравнения с Postgrees) латентностью.
  * **Встроенный TTL:** Нативная и эффективная поддержка автоматического удаления ключей по таймеру (`EXPIRE`).
* **Минусы:**

  * **Риск потери данных:** В случае аварийного перезапуска или сбоя репликации Redis существует вероятность потери части данных, находящихся в оперативной памяти, что приведет к мгновенному нарушению главного инварианта (риск двойных продаж).

### 3. Блокировка в Redis с TTL + подтверждение в PostgreSQL

* **Плюсы:**

  * **Снятие нагрузки с основной СУБД:** Вся конкурентная борьба за "захват" мест переносится в Redis. Запросы, которые "опоздали", отсекаются на уровне in-memory слоя, не доходя до реляционной базы данных.
  * **Гарантия персистентности:** Финальный статус успешной покупки фиксируется в надежном транзакционном хранилище PostgreSQL.
  * **Эффективное управление таймерами:** Механизм TTL в Redis автоматически решает задачу снятия резерва без необходимости запуска фоновых планировщиков над Postgress.
* **Минусы:**

  * **Усложнение архитектуры:** Необходимость обеспечения строгой согласованности (консистентности) между распределенным кэшем Redis и физической базой данных PostgreSQL на уровне прикладного кода.

## Решение

Выбран комбинированный подход: **Блокировка в Redis с TTL для краткосрочного резервирования в сочетании с записью в PostgreSQL**.

**Алгоритм работы схемы:**

1. При попытке занять место приложение выполняет атомарную операцию в Redis (например, `SET event:X:seat:Y user_id NX EX 600`).
2. Если Redis возвращает ошибку (ключ уже существует) — место занято, пользователю мгновенно отдается отказ. СУБД при этом никак не затрагивается.
3. Если ключ создан, приложение создает запись о брони в PostgreSQL со статусом `RESERVED`.
4. По истечении 10 минут (600 секунд) Redis автоматически удаляет ключ. Приложение слушает события истечения ключей (Redis Keyspace Notifications) либо проверяет статус брони при финальной оплате: если в Redis ключа уже нет, операция оплаты отклоняется, а статус в PostgreSQL меняется на `EXPIRED`.
5. При успешной оплате до истечения TTL — статус в PostgreSQL обновляется на `PAID`, а блокировка в Redis снимается.

## Обоснование

Данное решение балансирует между требованиями высокой производительности и абсолютной надежности. Перенос слоя конкуренции в Redis защищает PostgreSQL от деградации под огромным количеством потенциальных запросов в первые минуты старта продаж. В то же время дублирование факта брони в PostgreSQL гарантирует сохранность данных и финансовую отчетность.

## Последствия

* Необходимо реализовать проверку наличия и валидности Redis-блокировки в сервисе оплаты перед списанием денежных средств, чтобы не допустить проведение транзакции по просроченной брони.
* Приложение должно быть готово к сценарию "падения" Redis: код должен корректно обрабатывать исключения подключения к Redis, временно переключаясь на безопасный (пусть и более медленный) режим строгой валидации через PostgreSQL.
