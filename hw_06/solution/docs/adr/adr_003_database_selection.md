# ADR 003: Выбор СУБД для управления инвентарем мест и бронированиями

## Статус
Принято (Accepted)

## Контекст и проблема
Сервис бронирования должен гарантировать, что одно и то же место на мероприятии не будет продано двум разным пользователям одновременно (защита от double-booking). Требуется строгая транзакционность (ACID).

## Рассматриваемые альтернативы
1. **Реляционная СУБД (PostgreSQL)**
   - *Плюсы:* Полная поддержка ACID-транзакций, надежные механизмы блокировок строк.
   - *Минусы:* Труднее горизонтально масштабировать на запись по сравнению с NoSQL решениями.
2. **NoSQL СУБД (MongoDB / Cassandra)**
   - *Плюсы:* Высокая скорость записи, легкое горизонтальное масштабирование (шардирование).
   - *Минусы:* Отсутствие полноценной поддержки распределенных транзакций "из коробки" или компромиссы по модели CAP (выбор в пользу Availability вместо Consistency, что недопустимо для билетов).

## Решение
Выбрана реляционная СУБД **PostgreSQL**.

## Обоснование
Для бизнес-логики продажи билетов критически важна абсолютная консистентность данных. PostgreSQL предоставляет мощные механизмы блокировок и транзакций, гарантируя изоляцию конкурентных запросов на покупку одного места.

## Последствия
- Для масштабирования чтения будет применяться репликация (Master-Slave).
- Для защиты от долгих блокировок транзакций необходимо внедрить оптимистичную блокировку (Optimistic Locking) с использованием версионирования записей на уровне приложения, оставляя пессимистичные блокировки только для финального шага.
