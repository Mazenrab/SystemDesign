# ADR 005: Стратегия кэширования для каталога мероприятий

## Статус
Принято (Accepted)

## Контекст и проблема
Пользователи часто просматривают список доступных мероприятий и схему залов. Запросы к базе данных на чтение каталога создают высокую нагрузку на СУБД. При этом данные самого каталога (описания, даты, категории) меняются относительно редко, но должны отдаваться пользователям с минимальной задержкой для обеспечения отзывчивости интерфейса.

## Рассматриваемые альтернативы

### 1. Кэширование на стороне приложения (In-Memory в инстансах сервиса)
*   **Плюсы:**
    *   **Минимальная задержка:** Нулевые сетевые задержки при извлечении данных из локальной оперативной памяти.
    *   **Автономия:** Отсутствие зависимости от сторонних инфраструктурных компонентов кэширования.
*   **Минусы:**
    *   **Рассинхронизация данных:** Сложная инвалидация кэша на нескольких параллельных инстансах сервиса, что приводит к разным состояниям каталога для разных пользователей.
    *   **Утилизация памяти:** Повышенное потребление RAM внутри каждого контейнера приложения.

### 2. Распределенный кэш (Redis)
*   **Плюсы:**
    *   **Единый источник данных:** Общий актуальный кэш для всех горизонтально масштабируемых инстансов микросервиса.
    *   **Высокая производительность:** Быстрая работа с данными в памяти, поддержка атомарных операций и сложных структур.
    *   **Централизованная инвалидация:** Возможность мгновенного удаления или обновления ключей для всех узлов приложения одновременно.
*   **Минусы:**
    *   **Сетевой оверхед:** Появление сетевых задержек на запросы к Redis, хоть они и минимальны.
    *   **Дополнительная инфраструктура:** Необходимость развертывания, мониторинга и администрирования кластера Redis.

## Решение
Выбран **Распределенный кэш на базе Redis**. Для статических веб-страниц (публичные описания мероприятий) и статических медиа-ресурсов (афиши, изображения, неизменяемые базовые схемы залов) на внешнем контуре также будет задействован **CDN (Content Delivery Network)**.

## Обоснование
Использование Redis решает проблему консистентности кэша при динамическом горизонтальном масштабировании сервиса каталога. Инвалидация данных происходит централизованно (например, по событию изменения описания мероприятия организатором в админ-панели), гарантируя, что все пользователи увидят обновленный каталог синхронно.

## Последствия
*   **Реализация паттерна Cache-Aside:** Сервис Каталога должен строго следовать логике: чтение из кэша -> при промахе (Cache Miss) чтение из PostgreSQL -> запись актуальных данных в Redis -> возврат ответа клиенту.
*   **Настройка политик вытеснения:** Для Redis необходимо явно задать политику вытеснения данных `volatile-lru` (Least Recently Used) или `allkeys-lru` для предотвращения переполнения оперативной памяти.
*   **Управление временем жизни (TTL):** Для всех записей каталога в кэше должны быть настроены разумные тайм-ауты (Time-To-Live) во избежание эффекта "устаревания данных в случае сбоя механизмов явной инвалидации.
*   **Защита от лавинных эффектов:** Необходимо предусмотреть механизмы защиты от "прогрева кэша , когда при одновременном истечении TTL популярного мероприятия тысячи запросов не должны одномоментно упасть на основную базу данных PostgreSQL (распределенные блокировки на обновление данных, фоновое обновление кэша, предрасчёт).
