# ADR 005: Стратегия кэширования для каталога мероприятий

## Статус
Принято (Accepted)

## Контекст и проблема
Пользователи часто просматривают список доступных мероприятий. Запросы к базе данных на чтение каталога создают высокую нагрузку. Данные меняются не слишком часто, но должны отдаваться максимально быстро.

## Рассматриваемые альтернативы
1. **Кэширование на стороне приложения (In-Memory в инстансах сервиса)**
   - *Плюсы:* Нулевые сетевые задержки для получения кэша.
   - *Минусы:* Проблема инвалидации кэша на разных инстансах сервиса. Потребление оперативной памяти контейнера.
2. **Распределенный кэш (Redis)**
   - *Плюсы:* Единый источник правды для кэша всех инстансов приложения, высокая скорость работы в памяти, поддержка сложных структур данных.
   - *Минусы:* Появление дополнительного инфраструктурного компонента и сетевых задержек (хоть и минимальных) на обращение к Redis.

## Решение
Выбран **Распределенный кэш на базе Redis**. Для статических страниц (описание мероприятий) и для крайне редко изменяемых схем залов также будет задействован **CDN (Content Delivery Network)** на внешнем контуре.

## Обоснование
Redis решает проблему консистентности кэша при горизонтальном масштабировании сервиса каталога. Инвалидация кэша происходит централизованно (например, при изменении описания мероприятия организатором).

## Последствия
- Необходимо настроить политики вытеснения данных (LRU) и TTL (Time-To-Live) для записей в Redis.
- Сервис Каталога должен корректно обрабатывать сценарий "Cache Aside" (чтение из кэша -> при промахе чтение из БД -> запись в кэш).
