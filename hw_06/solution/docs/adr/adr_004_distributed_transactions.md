# ADR 004: Управление распределенными транзакциями (Паттерн Saga)

## Статус
Принято (Accepted)

## Контекст и проблема
Покупка билета включает шаги в нескольких микросервисах: резервирование места (Сервис Бронирования), списание средств (Сервис Оплат) и генерация билета (Сервис Билетов). Сбой на этапе оплаты требует отмены резерва места.

## Рассматриваемые альтернативы
1. **Двухфазный коммит (2PC - Two-Phase Commit)**
   - *Плюсы:* Гарантирует атомарность транзакции на уровне базы данных.
   - *Минусы:* Сильно блокирует ресурсы, создает узкое место по производительности, плохо масштабируется в микросервисах. Наличие единой точки отказа (координатор).
2. **Паттерн Saga (Оркестрация)**
   - *Плюсы:* Высокая производительность, отсутствие долгих блокировок ресурсов, явный контроль логики в одном месте (Оркестратор).
   - *Минусы:* Сложность реализации компенсирующих транзакций (откат изменений при сбое).
3. **Паттерн Saga (Хореография)**
   - *Плюсы:* Нет единой точки отказа, сервисы реагируют на события друг друга напрямую.
   - *Минусы:* Сложно отслеживать общую цепочку шагов при усложнении логики.

## Решение
Выбран **паттерн Saga на основе оркестрации (Orchestrator-based Saga)**. В качестве движка оркестрации будет использоваться специализированное решение (например, Temporal или Camunda), либо выделенный компонент внутри Сервиса Заказов.

## Обоснование
Оркестрация дает централизованный контроль над сложным процессом заказа билета. В случае неуспешной оплаты Оркестратор явно вызовет компенсирующее действие в Сервисе Бронирования для снятия резерва с места (`CancelSeatReservation`).

## Последствия
- Бизнес-логика должна проектироваться с учетом идемпотентности всех шагов Саги.
- Потребуется мониторинг "зависших" саг, требующих ручного вмешательства администраторов.
